What you'll see, step by step

  1. DataSynthetic telemetry from 50,000 trucks: sensors, route, age, and whether each truck failed. Failure causes are built in on purpose, so we know what the model should find.
  2. Train and trackA pipeline prepares the data, trains, evaluates and explains the model. Every run is recorded in MLflow. One run takes ~11 minutes; runs can be compared side by side.
  3. Quality gateA new model must be good enough and no worse than the current champion, or it stops here. A deliberately weak model scores 0.484 against a bar of 0.944: stopped, nothing registered.
  4. ApproveThe model waits in the registry until a person with the approver role signs off. The deployer role tries to approve and is refused by an explicit rule; the approver succeeds.
  5. Deploy safelyA new version gets 50 % of live traffic for 5 minutes while an alarm watches it. A broken version is rolled back automatically ~3 minutes in: 461 failed calls, then 0. Nobody touched it.
  6. MonitorEvery prediction is captured and checked for drift; real outcomes are joined in when they arrive. A change in fuel leaves every input looking normal, yet ranking quality drops from 0.97 to 0.65. Only the outcome check catches it.
  7. GovernLineage, a model card and the audit trail answer “where did this prediction come from, and who approved it?” From the live endpoint back to the exact training file in one command, cross-checked with SageMaker's own lineage.

Five things to take away

The platform can say no.

A weak model never reaches the registry, and a broken one never keeps live traffic.

People stay in control.

Approval is a separate role, enforced by IAM, recorded with who and why.

Accuracy lies when failures are rare.

The weak model is 96 % accurate and never predicts a failure. Every gate and alarm uses ROC-AUC instead.

Watch inputs and outcomes.

Input drift catches winter and a sensor fault. Only outcomes catch a changed failure cause.

Everything is code.

Infrastructure, pipelines and roles are versioned, repeatable and removed with one command.

5What makes a truck fail

The failure rules are built into the generator. The model is never told them; it has to discover them from the data:

  • Hot coolant above about 92 °C raises risk,
  • low oil pressure below about 380 kPa raises risk,
  • both at once raise it much more than the two added up,
  • a clogged DPF above about 12 kPa is the strongest single driver,
  • more engine hours and a vocational route add a little.

Failure rate in the training data by coolant temperature and oil pressure: from 0% for a cool engine with good oil pressure to 62% when the engine runs hot on low oil pressure. Either problem alone raises risk a little; together they raise it a lot.

Why this matters: the model can only be as good as the signal in the data. Building the rules in lets us check that it learned the right things (the explainability step shows it), and that the noise columns get ignored.

6Preparing the data

Cleaning: none needed here. The data is synthetic, so there are 0 missing values, no duplicates and every value sits in a physical range. That's deliberate: the demo is about the platform, not about data cleaning.

With real telemetry this step would also handle: sensors that drop out (missing values), spikes and stuck readings (outliers), mixed units (°F / °C, psi / kPa), duplicate uploads, and trucks with very short histories. It would be the same pipeline step, just with more inside it.

What the pipeline's first step does, every run:

1 · Split, keeping the failure rate

70 / 15 / 15 into training, validation and test, “stratified” so each part keeps the same share of failures.

2 · Turn route type into numbers

One category column becomes three 0/1 columns (long-haul, regional, vocational). 11 inputs become 13 numbers.

3 · Write the model's format

Label first, no header, numbers only: the CSV layout the XGBoost algorithm expects.

4 · Keep a reference copy

The training data, kept in readable form, becomes the yardstick that live traffic is compared with for drift.

Glossary

The words you'll hear in this demo, and why each one matters.

Feature
An input column the model learns from (oil pressure, route type …).Only what's in the features can be learned. Truck ID is not a feature.
Label
The answer the model is trained to predict: failure in the next 30 days, yes or no.Labels from the past teach the model; for new trucks it has to predict them.
Ground truth
The real outcome, known later (here: what the workshop found).Without it you can see that inputs changed, but not whether the model is still right.
Class imbalance
One answer is much rarer than the other: ~4 % of trucks fail.A model that always says “no failure” is 96 % accurate and useless. So we never judge by accuracy.
One-hot encoding
Turning a category into 0/1 columns: route type becomes three columns.Models need numbers. Training and serving must encode the same way, or answers silently change.
Stratified split
Splitting data so each part keeps the same failure rate.With rare failures, a careless split can leave the test set with almost none.
Train / validation / test
Learn on one part, tune on the second, judge once on the third.The test score is an honest estimate only if the model never saw those trucks.
ROC-AUC
How well the model ranks risky trucks above healthy ones. 0.5 = coin flip, 1.0 = perfect.The metric for the quality gate and the alarms. It isn't fooled by the 96 % that don't fail.
Inference
Asking the deployed model for an answer on new data.It's what the fleet system would call for each truck, in real time.
Data drift
Live inputs look different from the training data (winter, a sensor fault).Caught from the inputs alone, before outcomes are known.
Concept drift
Inputs look the same, but what causes failure has changed.Invisible to input checks. Only ground truth reveals it.
PSI
Population Stability Index: how far a column's distribution moved. Above 0.1 counts as drifted.One number per column, so you see which sensor changed.
Data capture
The endpoint saves every request and answer for later checks.It's what drift monitoring reads, and the audit record of what the model said.
Champion
The current approved model a new one has to beat.The quality gate compares every new candidate with it.

Why it's written this way
  • Labels are drawn as Bernoulli(sigmoid(z)) from the true physical values, so every truck has a known true risk. That's how step 1 can compare the model's 90 % with the built-in 91 %.
  • Each term is a hinge (np.maximum(0, …)): risk starts only above 92 °C coolant, below 380 kPa oil and above 12 kPa DPF. The hot * low_oil product is the interaction the heatmap shows.
  • The weights live in one settings dict (S.LABEL_MODEL), so the generator and the tests read the same numbers.
  • concept="fuel_blend" swaps the DPF term for a turbo term. That one branch is the whole concept-drift scenario.

Why it's written this way
  • It returns two frames: the true values, which decide the label, and what the sensors report, which goes to the model. Keeping them apart is what makes firmware a sensor fault instead of a real change.
  • Winter changes the truth, so the label follows. Firmware changes only the reading, so the label doesn't. Fuel blend changes no input at all, only the label logic.
  • Each dataset gets its own seed offset, so every batch is reproducible and independent of the others.

3The algorithm in plain words

XGBoost builds many small decision trees, one after another. Each new tree looks at where the model is still wrong and adds a small correction. The prediction is the sum of all the trees, turned into a probability.

The numbers are illustrative; the real model sums hundreds of trees.

The three settings we turn

max_depth

How many questions each tree may ask in a row. Deeper trees capture more detailed combinations, but can memorise noise.

eta

How big a step each new tree takes. Smaller steps learn more carefully but need more trees.

num_round

How many trees in total. More trees help until they don't, which the learning curve below shows.

Why XGBoost here: it's strong on tabular data like sensor readings, trains in about three minutes on one machine, and runs on AWS's managed XGBoost container. We pin that container to an exact image, so the same code produces the same kind of model next year.

Triggered by outcomes, not drift

Winter drifted hard and the model was fine. Retraining on every drift alarm would spend compute and change nothing.

Only useful with new labels

A retrain helps only if it learns from the trucks that broke under the new fuel, not from the same training file again.

It can't promote itself

Even an automatic retrain stops at the gate and at a person's approval, so a loop can't push a model to production.

10Honest about the demo

Shown from a recorded run

The four scenarios take about 37 minutes end to end, so they are presented from this recording. The runs, reports and alarm history can still be opened in the console.

Cleaner than real telemetry

Synthetic data gives a ROC-AUC near 0.97 that real trucks wouldn't. What matters is the change between scenarios, not the absolute number.

Why not SageMaker Model Monitor

It's closed to new customers. AWS's recommended path is this one: Data Capture, MLflow Apps and Evidently, with CloudWatch alarms.

Per column, not per dataset

Evidently's own “dataset drift” verdict needs half the columns to move, so its report says “not detected” for winter. The alarm here fires on one drifted column, the stricter rule for sensor data.

A pipeline with one step

A SageMaker Pipeline runs a processing job: read the captured calls for a time window, compare with the serving model's own training data, join the outcomes, write the results.

The right yardstick, found automatically

The job follows the endpoint to the model version it serves and to that version's training data, so a new deployment changes the reference by itself.

Both alarms and the email topic are part of the infrastructure code; each alarm keeps the latest run's verdict until the next one.

Canary, smoke and Predict-panel calls carry their own ID prefixes and are never counted as live traffic.

Glossary

New words in this step, and why each one matters. Step 1 has the basics.

Data drift
Live inputs no longer look like the training data.The first sign the model is being asked about a different world.
Prediction drift
The model's answers shift: more or fewer trucks flagged, higher or lower risks.Visible without waiting for outcomes, but only if the inputs moved.
Concept drift
The inputs look the same, but what they mean for the outcome has changed.Invisible to every input check. Only real outcomes reveal it.
Reference sample
The training data of the model now serving, kept as the yardstick.Live traffic is always compared with what this exact model learned from.
PSI
Population Stability Index: one number for how far a column's distribution moved. 0.1 or more counts as drifted here.A single, comparable score per sensor, so the report can point at the one that moved.
KS, Wasserstein, chi-square
Other standard ways to compare two distributions, reported next to PSI.Different tests, same question; useful when someone asks “by which measure?”
Ground truth
What really happened to each truck, reported later by the workshop.Without it you can see that inputs changed, but not whether the model is still right.
Join
Matching each prediction to its outcome by the inference ID the caller sent.One shared ID turns two separate records into a scored prediction.
Recall
Of the trucks that really failed, the share the model flagged.The number that falls first when a sensor lies.
Sample size
How many calls a drift check looks at.Too few, and every column looks drifted by chance.

9Honest about the demo

Addresses, not contents

Three read-only commands

One walks the lineage, one reads CloudTrail, one writes the model card from live state. Each takes seconds.
